Architectural Decisions

The significant design choices made in ReWinds, and why they were made.

These decisions were reconstructed from the codebase during the bootstrap phase (2026-06-09). Original ticket history was not available for all entries.
Active

iOS Keychain for API key storage

2026-06-09

Why this was needed

The app requires two API keys at runtime: one for Anthropic (AI chat) and one for Visual Crossing (weather data). On Android, keys are injected at build time via gradle.properties → BuildConfig. iOS has no equivalent mechanism that works without rebuilding the app, which makes it impractical for end users to supply their own keys.

What was decided

On iOS, API keys are stored in the iOS Keychain using kSecAttrAccessibleWhenUnlockedThisDeviceOnly. A build-config override is also supported via Info.plist / Config.local.xcconfig (gitignored) for developer convenience. At startup the app checks the build config first, then the Keychain, and finally falls back to empty — which triggers a Settings prompt.

The Kotlin↔Swift bridge uses a callback pattern: Kotlin bridge objects hold Swift-registered closures for save and delete. When the user saves a key in Settings, the Kotlin actual function invokes the registered Swift closure, which writes to the Keychain using the native Security framework. This keeps iOS-specific Security API code in Swift, where it is most natural.

Trade-offs accepted

  • Keys stored with kSecAttrAccessibleWhenUnlockedThisDeviceOnly do not migrate via iCloud Keychain. Users must re-enter keys after migrating to a new device.
  • The Visual Crossing key has no build-config path on iOS and must always be entered in Settings by iOS users.
  • Android remains build-time-only for keys; runtime configurability was not added there.

Gradle iOS build exclusion by default

2026-06-09

Why this was needed

Kotlin/Native iOS Gradle tasks (linkPodReleaseFrameworkIosSimulatorArm64 and siblings) were unreliable. They compile Kotlin to a framework binary but do not go through Xcode's build system — no CocoaPods integration, no correct iOS SDK paths, no full Xcode build settings. Running them in the default build added compile time and periodically crashed with podspec/generateDummyFramework errors, blocking Android-only development.

What was decided

iOS targets are excluded from ./gradlew build unless -PincludeAllTargets=true is explicitly passed (intended for CI). A convenience task buildAndroidOnly was added to make the intent clear. The canonical iOS build tool is Xcode: open iosApp/iosApp.xcworkspace and press Cmd+R.

Apple Silicon only: the iosX64 (Intel simulator) target was removed. Only iosArm64 and iosSimulatorArm64 are built.

Trade-offs accepted

  • Developers must switch tools when moving between Android and iOS work — Gradle for Android, Xcode for iOS.
  • CI pipelines that need iOS builds must pass the flag explicitly.
  • The Kotlin/Native compiler daemon is kept enabled (not disabled) to keep build performance reasonable when iOS targets are compiled in CI.
  • Devirtualization is disabled (-Xno-devirtualization) to work around a Kotlin/Native runtime issue. This is a known performance trade-off.

Three-layer AI data fetch permission gate

2026-06-09

Why this was needed

The AI chat can ask the app to fetch weather data from Visual Crossing on the user's behalf. Visual Crossing charges per query. A question like "what were wind conditions in Tarifa all of last year?" would silently trigger 12 months of API calls without the user realising. Users should be aware before the app makes external calls that cost money and take time.

What was decided

The get_weather_metrics tool implements a three-step flow before any network fetch:

  1. Check local database availability (Available / Partial / Missing).
  2. If not fully available, return a structured permission_required response to the AI instead of fetching. The response includes the location, date range, and a human-readable explanation.
  3. The chat UI surfaces this as a user prompt. On confirmation the app fetches the data directly, then asks Claude to retry the original question.

If data is already fully in the local database, the gate is bypassed and the tool responds immediately at zero cost.

Trade-offs accepted

  • The permission detection uses both a structured JSON check and a regex fallback on the AI's response text. The regex is fragile if the model's phrasing changes in a future API version.
  • The gate is only on get_weather_metrics. The get_wind_summary, get_monthly_stats, and get_best_days tools call the database directly without a permission step.
  • Context chips in the chat UI do not currently constrain which data Claude can access — they are visual-only as of the current build.

Gap-fill caching strategy for weather data

2026-06-09 · KIM-278

Why this was needed

Weather data is expensive to fetch. As users accumulate data for multiple places over multiple years, loading all days and hours on every Home screen visit became too slow. The Home screen was noticeably sluggish with more than a handful of places, because it was loading full day and hour rows on every visit.

What was decided

Three complementary strategies were adopted:

  1. Home screen lightweight query. The Home screen uses a single GROUP BY SQL query that returns only the day count per place — no day or hour rows are loaded. This scales to any number of places with constant cost.
  2. Session-lifetime in-memory cache. After the first full load of a place's data (e.g. when navigating into Place Summary), the complete WeatherResponse is cached in memory for the remainder of the app session. Navigating away and back skips the database entirely. The cache is invalidated whenever new data is written for a place.
  3. Gap-fill queries. When fetching a date range, the app first checks which dates are already in the database and requests only the missing consecutive gaps from the API — never refetching data that is already present.

Trade-offs accepted

  • The in-memory cache has no eviction policy. Memory usage grows with the number of distinct places visited during a session. It is cleared only on app restart.
  • Every write path must go through persistAndInvalidate(), which enforces cache invalidation. A write that bypasses this function would serve stale cached data.
  • getPreviousDays always fetches from the network without a DB-first check — this is intentional for the "recent live data" use case but means it always costs an API call.

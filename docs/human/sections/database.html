Database & Data Models

Local persistence, weather data shapes, and how records are stored and queried.

Storage technology

All data is stored locally on the device in a single SQLite database named app.db. The schema and queries are defined using SQLDelight, which generates type-safe Kotlin functions at compile time. There is no cloud sync or server-side storage — the database is entirely local.

The database holds four categories of data:

  • Weather records — places, daily weather (one row per day per place), and hourly sub-records.
  • Weather stations — nearby measurement stations for each place, used on the station map.
  • Chat history — sessions and individual messages for the AI chat.
  • App settings — key/value store for the days-of-interest filter and other preferences.

On iOS, SQLite is provided as a native C library via CocoaPods. On Android, the standard Android SQLite driver is used. Both platforms share the same schema file located at composeApp/src/commonMain/sqldelight/.

Write semantics

Weather data uses upsert semantics — new places and new days are inserted; existing days are never overwritten. This means partial downloads accumulate safely: if you download January and then February separately, both months end up in the database without any data loss.

Station data uses a delete-then-insert approach within a single transaction. When station data is refreshed, all existing station rows for a place are removed and the new set is inserted atomically.

Every write operation invalidates the in-memory session cache for the affected place, so the next read always reflects the latest database state.

Core data models

WeatherResponse

The top-level container for a place's data. The resolvedAddress field is used as the canonical place key throughout the app — it is the key for cache lookups, database queries, and tool calls.

Day

One calendar day of weather data, matching the Visual Crossing day object. A day record includes:

  • Temperature: min, max, average, feels-like variants — all in Celsius.
  • Wind: daily average speed, gust, and direction — stored in m/s as received from the API. Display layers and the AI tools convert to knots where needed (multiply by 1.944).
  • Precipitation: amount (mm), probability (%), coverage (%), type (e.g. "rain"), snow depth.
  • Atmosphere: humidity, dew point, pressure (hPa), cloud cover (%), visibility (km).
  • Solar: radiation (W/m²), energy (MJ/m²), UV index.
  • Astronomical: sunrise/sunset times, moon phase (0.0–1.0).
  • Conditions text and icon identifier.
  • A list of hourly records (Hour) covering the full day.

Hour

One hour within a day. Contains the same weather fields as a day record (temperature, wind, precipitation, atmosphere, solar) but without day-level aggregates like min/max temperature or sunrise/sunset.

Station

A physical weather measurement station near a saved place. Stores its name, coordinates, distance from the place (in metres as returned by the API — the display layer divides by 1000 for km), data quality score, and usage count.

DayWeatherSummary

A derived display model produced by the Place Summary and Monthly Statistics ViewModels from a Day record. It is not persisted — it is computed on read. Fields include pre-calculated sustained wind speed (a rolling average over a configurable window of hourly records), fog detection, and whether the day matches the current days-of-interest filter (isMatch).

Performance design

Loading all days and all hours for a place in one query is expensive as data accumulates. Two strategies keep the app responsive:

  • Home screen lightweight query. The Home screen never loads full day rows. It uses a single GROUP BY SQL query that returns only the day count per place. This is fast regardless of how much data is stored.
  • Session-lifetime in-memory cache. After the first full load of a place's data (e.g. when opening Place Summary), the result is cached in memory for the rest of the app session. Navigating away and back does not trigger another database read. The cache is invalidated whenever new data is written for that place.
The cache has no eviction policy. Memory usage grows with the number of places visited in a session. It is cleared only on app restart.

Gap-fill queries

When the app needs weather data for a date range — either from the AI tools or from a manual month download — it does not blindly re-fetch everything. Instead it compares the requested range against what is already in the database and fetches only the consecutive gaps. Each gap is a separate Visual Crossing API call.

This means repeated requests for overlapping date ranges cost nothing after the first fetch, and partial month downloads accumulate correctly.

Export and import

The app supports backing up and restoring the database file. This is exposed through the debug panel on the Home screen. The implementation is platform-specific (DatabaseExportImport expect/actual): on iOS it copies the SQLite file to the app's documents directory; on Android it copies to external storage. The three operations are export, import (by file path), and list backups.

App settings storage

Settings (currently the days-of-interest filter JSON) are stored as key/value rows in the same SQLite database via AppSettingsRepository. Reads and writes are simple string get/set operations — no separate preferences file is used.

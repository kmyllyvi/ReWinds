Architecture

Platform layers, module dependencies, and data flows.

Platform layers

ReWinds uses Kotlin Multiplatform with three source sets. Almost all logic lives in commonMain. Platform source sets contribute only what the platform mandates: SQLite driver initialisation, Keychain access on iOS, and the Android Activity entry point.

Module dependency graph

Dependencies flow strictly downward. The UI layer knows only ViewModels; ViewModels know only Repositories; Repositories talk to infrastructure. No layer may import from a layer above it.

Screen structure

The app uses a three-tab navigation scaffold. Each tab manages its own independent push stack via NavigatorImpl.

Weather data lifecycle

Data is fetched lazily and stored in SQLite. On every subsequent open, the database is the source of truth — the network is only hit for genuinely missing date ranges (the gap-fill strategy).

User searches location
  → HomeViewModel.onSearchResultSelected()
  → WeatherRepository.addPlaceFromSearch()      (Open-Meteo geocoding → Visual Crossing)
  → SqlDelightDatabase.saveWeatherResponse()    (persisted to SQLite)
  → HomeViewModel.loadSavedPlaces()             (lightweight GROUP BY count query)

User opens a place
  → PlaceSummaryViewModel.loadWeatherData()
  → WeatherRepository.getSavedDataFor()         (session cache → SQLite full load)
  → [auto] WeatherRepository.fetchAndPersistStations()

User downloads a month
  → WeatherRepository.downloadFullMonth()
  → WeatherRepository.getDaysRange()            (gap-fill: DB check → network per gap)
  → SqlDelightDatabase.saveWeatherResponse()    (upsert; existing days not overwritten)

AI chat data flow

The chat uses an agentic loop — Claude calls weather tools, the app resolves them against the local database, and Claude synthesises an answer. If data is missing, a three-layer permission gate asks the user before making any external API call.

User sends message
  → ChatViewModel.sendMessage()
  → AiRepository.sendMessage()                  (agentic loop, max 20 turns)
  → AnthropicClient.sendMessage()               (POST /v1/messages, claude-haiku-4-5)
  → [if tool_use] WeatherTools.handleToolCall()
  → WeatherRepository / Database query
  → [if data missing]
      1. DataAvailability.check()
      2. Return permission_required response to user
      3. User confirms → WeatherRepository.getDaysRange() → fetch
      4. Retry original tool call
  → Claude synthesises final answer
  → ChatRepository.saveMessage()                (persisted per session in SQLite)

Build system

The default Gradle build (./gradlew build) produces Android only. iOS is built through Xcode using the .xcworkspace — CocoaPods manages the native sqlite3 library and the Kotlin/Native framework. See the iOS Platform section for details.

Key conventions

  • No business logic in composables. All state decisions live in ViewModels. Composables are pure renderers.
  • Navigation uses a per-tab back stack (mutableStateListOf<NavRoute>) wrapped by NavigatorImpl. Navigator is not injected via Koin — it is passed explicitly.
  • Platform expect/actual is used for: DatabaseDriverFactory, DatabaseExportImport, httpClient, getAnthropicApiKey, getVisualCrossingApiKey, saveApiKeyPlatform, deleteApiKeyPlatform, and language persistence.
  • Dark mode only. The app does not support a light theme. iOS forces dark mode at the system level. No .background() on page-level views — only on self-contained components (e.g. ChatInputArea).

iOS Platform

Build setup, Keychain integration, and iOS-specific implementation details.

Building for iOS

The canonical tool for iOS builds is Xcode. Always open the workspace file, not the project file — CocoaPods requires the workspace to wire in native dependencies like sqlite3.

# Open the workspace
open iosApp/iosApp.xcworkspace

# Then press Cmd+R to build and run on the simulator

Alternatively, from the command line:

xcodebuild \
  -workspace iosApp/iosApp.xcworkspace \
  -scheme iosApp \
  -configuration Debug \
  -sdk iphonesimulator \
  -derivedDataPath build
Do not use ./gradlew build for iOS. Gradle iOS tasks only compile the Kotlin framework — they do not run through Xcode's build system, do not apply CocoaPods integration, and do not produce a runnable app. They have been excluded from the default build.

Why Gradle skips iOS by default

Running ./gradlew build without flags builds Android only. iOS targets are included only when -PincludeAllTargets=true is passed, which is intended for CI pipelines.

This was a deliberate decision: Kotlin/Native iOS Gradle tasks were unreliable — they compiled Kotlin to a framework binary but had no proper CocoaPods integration, incorrect iOS SDK paths, and occasionally crashed with podspec/generateDummyFramework errors. Removing them from the default build eliminated a whole class of build failures and made local development faster.

A convenience task ./gradlew buildAndroidOnly makes the intent explicit for Android-only builds.

CocoaPods and the sqlite3 dependency

The iOS app uses CocoaPods to manage the native sqlite3 library required by SQLDelight's Kotlin/Native driver. The Podfile is at iosApp/Podfile; Pods are committed (at iosApp/Pods/).

The composeApp.podspec file defines the Kotlin framework as a CocoaPods vendored framework. This means Xcode's build system handles all framework linkage automatically.

Do not manually add -framework ComposeApp to OTHER_LDFLAGS in Xcode build settings. The podspec's vendored_frameworks entry already handles all linkage. Adding it manually causes duplicate symbol errors at link time.

API key storage — Keychain

iOS does not have a build-time key injection mechanism that works without recompiling the app. To let users configure their own API keys, ReWinds stores them in the iOS Keychain using kSecAttrAccessibleWhenUnlockedThisDeviceOnly.

Two keys are stored separately:

  • Anthropic API key — Keychain account: anthropic_api_key, service: com.km.rewinds.
  • Visual Crossing API key — Keychain account: visual_crossing_api_key, same service.

At app startup, the priority order for the Anthropic key is:

  1. Build-time value from Info.plist key ANTHROPIC_API_KEY (populated via Config.local.xcconfig, which is gitignored and must be created manually per developer).
  2. Value stored in the Keychain from a previous Settings save.
  3. Empty — triggers the Settings prompt in the Chat tab.

The Visual Crossing key has no build-config path on iOS; it must always be entered in Settings.

Keys stored with kSecAttrAccessibleWhenUnlockedThisDeviceOnly do not migrate via iCloud Keychain backup. Users who switch to a new iPhone must re-enter their API keys.

Kotlin ↔ Swift bridge pattern

Apple Security framework APIs are simpler to call from Swift than from Kotlin/Native C interop. Rather than bridging the Security framework directly into Kotlin, the design uses a callback pattern:

  1. Swift registers closure callbacks with Kotlin bridge objects (KeychainBridge, WeatherKeychainBridge) at startup.
  2. When the Settings screen saves or deletes a key, the Kotlin actual function invokes the registered Swift closure.
  3. The Swift closure calls KeychainHelper.swift, which wraps the Security framework.

Wrapper functions in iosMain Kotlin (IosKeychain.kt, IosWeatherKeychain.kt) expose these to Swift as top-level functions, since Swift cannot directly call into Kotlin singleton objects from the compiled framework.

iOS startup sequence

The full sequence in iOSApp.swift at launch:

  1. Check Info.plist for a build-time Anthropic key. If present, load it into the in-memory key store.
  2. Otherwise, load the Anthropic key from the Keychain.
  3. Register Swift Keychain callbacks for future save and delete actions.
  4. Load the Visual Crossing key from the Keychain.
  5. Register Visual Crossing Keychain callbacks.
  6. Initialise the SQLite database driver (DatabaseDriverFactory).
  7. Initialise Koin DI with the database driver.
  8. Initialise the Napier logger.
  9. Present the Compose root view controller (dark mode forced via .preferredColorScheme(.dark)).

Apple Silicon only

The project targets iosArm64 (physical devices) and iosSimulatorArm64 (Apple Silicon simulator). The iosX64 target (Intel Mac simulator) has been removed. Device ARM64 builds are memory-intensive — they require 8 GB or more of JVM heap and may OOM on machines with less RAM or without sufficient swap.

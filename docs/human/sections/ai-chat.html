AI Chat

How the conversational weather assistant works under the hood.

Overview

The AI chat feature connects to the Anthropic API using the claude-haiku-4-5 model. Claude is configured as a wind-sports analyst: it knows how to interpret weather data in the context of kitesurfing and windsurfing, and it uses a set of tools to query the app's local SQLite database rather than making up answers.

Each user message triggers an agentic loop that can run up to 20 turns. Within those turns Claude can call tools multiple times, combine results, and reason across several locations or date ranges before producing its final answer.

Available tools

Five tools are registered with every Claude request:

ToolWhat it does
get_weather_metrics Fetches one or more specific metrics (temperature, humidity, wind speed, UV index, etc.) for a location and date range. This tool implements the full three-layer permission gate before any network fetch.
get_wind_summary Returns a structured wind summary for a location and date range — speeds, gusts, direction, and sustained-wind hours.
get_monthly_stats Returns aggregated statistics for a single calendar month: temperature extremes, rainfall, solar energy, average wind.
get_best_days Finds days within a date range that meet optional criteria: minimum/maximum wind speed (in knots), maximum gust, and no-rain flag.
list_saved_places Returns the names of all saved places. Useful for Claude to know what data is available before asking follow-up questions.

Metric names passed by Claude are translated to database field names by MetricMapper, which understands approximately 50 alias variants. Wind values are stored in m/s and converted to knots (multiplied by 1.944) for display and for tool parameters that use knots.

The permission gate

Fetching weather data from Visual Crossing costs API credits and takes time. To keep the user in control, get_weather_metrics implements a three-step permission flow before making any network call:

  1. Availability check. Before fetching, the tool asks the local database whether the requested data already exists (Available, Partial, or Missing).
  2. Permission request. If data is not fully available, the tool returns a structured response with "status": "permission_required", the location, the date range, and a human-readable explanation — instead of fetching.
  3. User confirmation. The chat UI surfaces this as a prompt. If the user confirms (typing "yes", "ok", "proceed", etc.), the app fetches the data directly, then asks Claude to retry the original question with the data now in the database.
If the data is already fully available in the local database, the permission gate is bypassed entirely and the tool responds immediately with no network call.
The other three tools (get_wind_summary, get_monthly_stats, get_best_days) do not implement the permission gate — they call the database directly. Only get_weather_metrics has the full three-layer flow.

Chat persistence

Conversations are stored in SQLite through ChatRepository. Each app session has a session record; messages within it are saved as they are sent and received. When the app restarts, the last session's history is loaded so the conversation continues where it left off.

The AI keeps the conversation history in memory during the agentic loop and passes it with every request to Claude, providing full context. History is reconstructed from the database as plain text blocks on reload — multi-part tool-use turns from previous sessions are simplified to text for the history reconstruction.

API key setup

The chat feature requires an Anthropic API key. How this is configured depends on the platform:

  • iOS: Enter the key in the Settings tab. It is stored securely in the iOS Keychain and persists across restarts. Optionally, a build-time key can be embedded via Config.local.xcconfig for developer builds.
  • Android: The key is set in gradle.properties at build time and compiled into the app via BuildConfig. It cannot be changed at runtime through the UI.

If no key is configured, the chat screen shows an inline prompt to open Settings.

Known limitations

  • Context chips visible in the chat UI do not currently filter which data Claude receives — they are a UI-only element as of the current build.
  • The permission detection in the app uses a regex fallback on the AI's response text, which may be fragile if the model's phrasing changes in a future API version.
  • History reconstruction from the database simplifies tool-use turns to text. If you clear and reload a long session, the full structured tool history is not preserved.

Anthropic API request/response shape

Each request to /v1/messages includes the model, the system prompt, the full conversation history, and the five tool schemas. Responses may have a stop reason of end_turn, tool_use, or max_tokens. The agentic loop continues as long as the stop reason is tool_use and the turn count is below the limit.

Errors with HTTP status 401 or 403 are surfaced to the user as an "invalid API key" message with a link to Settings. Other errors show a generic dismissible error banner.
